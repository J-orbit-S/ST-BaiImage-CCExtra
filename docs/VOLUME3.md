# VOLUME 3 · 漫画页（N 段 → 一页 N 格）

> 状态：**讨论稿，未落地**。本文只定「做什么、为什么这么做、指引怎么写」，不含实现。
> 覆盖范围：① 漫画页的准确定义 ② 柏宝绘已经做到哪一步 ③ 三条技术路线 ④ 分格几何归谁算
> ⑤ 提示词 / 思维链 / 中文对照怎么写 ⑥ 页数与操作粒度 ⑦ 待拍板的问题。

**结论先行**：能做，而且**不需要改柏宝绘一个字节**——但要先接受一个硬前提：
**漫画页只能走「漫画方案 + MOSS-Image 后端」**。这不是我们的选择，是柏宝绘出图链路的
强校验（`generate.ts:219`）。接受它之后，V3 的增量其实只有两件事：
**原料从「整楼」换成「你挑的 N 段」**，以及**把页数往「一页」上收**。

---

## 1. 你想要的到底是什么

原文：

> 一整楼的剧情里面，我挑两个/三个/几个连贯的瞬间，通过拼接的方式，有可能是四格漫画
> 也有可能是别的，生成一张图。

拆成四条判据，后面每一条都要能对上：

| # | 判据 | 含义 |
|---|---|---|
| 1 | **选段由人定** | 画哪几个瞬间是用户决定的，不是模型从整楼里自己挑 |
| 2 | **一次成图** | N 段合成**一张**，不是 N 张（那是 V2.1 的批量） |
| 3 | **格数可变** | 四格是常见形态，但不是唯一；2 / 3 / 6 格都要能出 |
| 4 | **叙事连贯** | 格与格之间是同一段剧情的先后，共享角色、服装、光线、画风 |

### 1.1 和已有功能的区别（三者容易混，必须分清）

| | 输入 | 输出 | 额度 | 现状 |
|---|---|---|---|---|
| 单插图（v0.1） | 1 段 | 1 张图 | 1 次副 API + 1 张图 | 已上线 |
| 批量（v0.2.2） | N 段（同楼） | **N 张**图 | 1 次副 API + N 张图 | 已上线 |
| 柏宝绘漫画方案（原生） | **整楼** | 若干**页**，每页 3~5 格 | 1 次副 API + 页数张图 | 已上线（但要 MOSS） |
| **漫画页（V3）** | **N 段（人挑的）** | **1 页**（希望） | 1 次副 API + 1 张图 | 未做 |

注意第三行：**柏宝绘自己已经会画多格漫画了**，只是它吃整楼、自己挑瞬间、页数不固定。
我们的增量是「把挑选权拿回来 + 把页数压到 1」。这个定位很重要——否则容易重复造它已有的东西。

## 2. 硬前提：漫画页只能走漫画方案（MOSS-Image）

这一条必须先讲，因为它决定「谁能用这个功能」。

柏宝绘的漫画不是「用插画模型画四个格子」，而是一套独立链路：

- 协议不同：插画是 `images[] + tag`，漫画是 `pages[] + layout`；
- 正文格式不同：`<bbi_image><type>comic</type><layout>{…JSON…}</layout><size>…</size></bbi_image>`；
- 提示词不同：`comicContract` 整段替换插画那套（`prompt.ts:364`）；
- 后端不同：layout JSON 只有 **MOSS-Image** 吃得下（`mossLayout.ts` 换算成它以画布中心为原点的像素坐标）。

而且这个校验是**双向硬拒**的（`generate.ts:219-220`）：

```
这是漫画分镜，当前出图方案不是漫画方案   ← comic 标签落在插画方案上
当前出图方案是漫画方案，不能画插画 tag   ← 反过来也不行
```

**推论（三条，都要写进 README 和面板文案）：**

1. **没有 MOSS-Image 后端的用户，这个功能用不了**——不是「效果差一点」，是直接报错。
   所以入口要有前置判断：当前方案不是漫画 → 漫画页选项灰掉，悬停给原因，
   而不是让他点了才发现写不进去。
2. **不能「悄悄改用插画模型凑四格」**（那是下面的 B 案）。两条链路的 tag 语义完全不同，
   混用等于让模型猜，失败时用户看到的是「图很怪」而不是「报错」，更难排查。
3. **写回正文的东西必须仍是合法 comic 标签**，让柏宝绘的卡片、promptHash、图库全部照旧认领。
   我们只在「送进去的原料」和「页数」上做文章，不碰落盘格式。

> 这也解释了现有的一处限制：`analysis.ts:463` 现在遇到漫画方案会直接拒绝批量
> （`comic-batch-unsupported`）。不是没做，是**批量（N 段 N 张）和漫画（N 段 1 页）
> 是同一入口的两种渲染目标**，得先把岔路口设计出来。

## 3. 柏宝绘已经做到哪一步（不要重造）

`comicContract` 里这几句是现成的、写得相当好，我们应当**直接受用**：

| 现有规范 | 对我们的意义 |
|---|---|
| 「把目标正文改编成漫画，至少一页」 | 页数下限有，上限没有 → 见 §8 |
| 「漫画是精选改编，不是逐段图解……不必每段都有对应的格」 | **和我们的需求正相反**：我们要每段至少一格 → 见 §7 指引 |
| 「每页 3～5 格」 | 直接决定 N 的可用范围（2～5 段最顺） |
| 「一楼正文通常 1～2 页就够」 | 压一页有基础，但不是硬保证 |
| 「caption 以动作开头，不写 the girl / she」 | 我们写分格指引时要遵守，不能自己发明句式 |
| 「同一角色同一套临时服装逐字复用」 | 跨格一致性已在规范里，不用我们重复要求 |

**还有一条容易被忽略的事实**：我们现在的划线出图，在漫画方案下**已经能出漫画页**了
（`runSelection` 走 `pages[]`），只是原料是「划的那一段」，出来的往往是「一段一页」。
所以 V3 不是从零做漫画，而是把「一段 → 一页」升级成「N 段 → 一页」。

**V3 的增量就此收敛为两件：**

1. 一次分析吃 **N 段**（复用 V2.1 的伪楼层拼装层）；
2. 输出**收敛到一页**（软约束 + 兜底出口）。

## 4. 三条路线（选一条，A 推荐）

| | A. 复用漫画方案 | B. 插画模型硬拼格 | C. 本地拼图后处理 |
|---|---|---|---|
| 做法 | N 段拼伪楼层 → comicContract → 一页 layout | 在 tag 里写 `4koma, multiple panels, split screen` | N 段各出 1 张 → 前端拼成一张长图/四格 |
| 改动量 | 小（拼装层现成） | 中（协议不变，但要发明 tag 语义） | 大（新落盘路径 + 新展示层） |
| 出图质量 | 高（MOSS 就是为此而生，格内构图统一） | **不稳**：模型没有格线概念，容易画成「一张挤了四个人的图」 | 中：像「四张图贴一起」，无跨格构图、光照不统一 |
| 失败表现 | 报错清晰（方案不对） | 图很怪但不报错 → **最难排查** | 排版丑但不报错 |
| 与柏宝绘的关系 | 零改动，完全复用它 | 绕开它的漫画链路，等于自己造协议 | **另开一条落盘路径**（违反「出图只走柏宝绘卡片」的红线） |
| 结论 | **推荐** | 仅作「没有 MOSS 时的降级提示」，不实现 | **不做** |

**为什么 C 直接否掉**：它产生的不是漫画，是一张拼贴图。真正让漫画读起来连贯的是
**跨格的统一画风、共享角色、连续光线**——这只有「一次生成、一次构图」才能保证。
而且 C 要在本地新开一条出图/落盘路径，直接违反项目红线（见 README 边界表最后一行）。

**B 留一个口子**：如果用户没装 MOSS，面板可以提示「漫画页需要漫画方案（MOSS-Image）」，
并给一个「了解」链接，**但不偷偷降级**。

## 5. A 案数据流

```
待生成列表（N 段，同楼）
      │  复用 V2.1 拼装层
      ▼
伪楼层：段1 + 段界标记 + 段2 + 段界标记 + … + 段N
      │  prepareTargetText → 全局重编 P1..Pn
      ▼
一次副 API 调用（comicContract + taskNote 追加「每段至少一格、按序、只出一页」）
      ▼
pages[] → 我们收成一页 → layout{summary, items[]}
      ▼
一张候选（segments[] 长度 N）→ 确认 → 写回 <type>comic</type> → 柏宝绘卡片出图
```

### 5.1 段界标记在漫画里是双刃剑

V2.1 的段界标记（`——〔第 2 段〕——`）在批量里是好东西，在漫画里要**格外小心**：

- 好处：模型能看清「这里有 N 个片段」，天然对齐「一段一格」；
- 风险：`comicContract` 明说「漫画是精选改编，不是逐段图解」，段界标记会强化
  「逐段图解」的倾向，可能让模型把过渡句也画成一格（我们要的是「每段一格」，不是「每句一格」，
  这个度只能靠 taskNote 说清楚）。

**处理原则**：段界标记保留，但 taskNote 里必须补一句「标记只是片段分界，不是漫画分格线；
每段选一个最有画面感的瞬间，格数 = 段数」。这句话是 V3 指引的核心（见 §7）。

### 5.2 出处：`position` 单值装不下「一页来自 N 段」

协议里 `pages[i].position` 是单值，一页只能声明锚在一个位置。所以：

- 写进正文的 `position` 取**第一段**的位置（页面插在这里，符合阅读直觉）；
- 真实的「这一页取材于哪几段」记在**我们自己的** `segments[]`（V2.1 已经为此把模型改成图优先，
  一次改造现在收利息）；
- 卡片头写「第 12 楼 · 3 段」，点一下能逐段回指原文。

## 6. 分格几何：bbox 该由谁来算（V3 最值钱的一条建议）

### 6.1 现状的问题

MOSS layout 的 `items[].bbox` 是 0–1000 归一化坐标，**现在由模型写**。模型的空间感很差：

- 格子重叠、出界、大小悬殊；
- 四格写成「三格挤上面、一格占满下半页」；
- 同一段剧情两格之间没有留白，读起来像一张图。

修不好，因为它不是「模型不听话」，是**这种数值约束本就不该由语言模型算**。

### 6.2 建议：几何我们算，内容模型写

按段数查表，我们直接给出 bbox；模型只负责每格的 caption。

| 段数 | 版式 | bbox（y0, x0, y1, x1，留 2% 沟槽） |
|---|---|---|
| 2 | 上下均分 | `[0,0,490,1000]`、`[510,0,1000,1000]` |
| 3 | 上大下二 | `[0,0,560,1000]`、`[570,0,1000,490]`、`[570,510,1000,1000]` |
| 4 | 2×2 四格 | `[0,0,490,490]`、`[0,510,490,1000]`、`[510,0,1000,490]`、`[510,510,1000,1000]` |
| 5 | 上二下三 | `[0,0,490,490]`、`[0,510,490,1000]`、`[510,0,1000,330]`、`[510,340,1000,660]`、`[510,670,1000,1000]` |
| 6 | 2×3 | 按 §6.5 竖切三等分 |

同时给 `summary` 前置一句版式声明（保留模型写的画风/光线，只加前缀）：

```
full color manga page, {N}-panel layout with visible panel borders and white gutters, reading order top to bottom — {模型原文 summary}
```

### 6.3 代价（需要你点头）

- 写回正文的 `layout.bbox` **不再是模型原样**，而是我们后处理过的（和 rebase 同类性质：
  我们维护的是「落盘数据」，不是「分析口径」）；
- 这一步**只在我们自己的后处理层**，柏宝绘的 `validateComicLayout` / `buildMossPrompt` 一行不动，
  它读回去仍然是合法 layout；
- 需要实测确认：**MOSS 是否服从 "panel borders and white gutters" 这句话**。
  它是 layout 模型，「分格线」属于 summary 的语义，不是 bbox 的几何——**如果实测不画格线，
  就退回「让模型自己写 summary」，只保留 bbox 模板**（几何至少不重叠）。

> 这一条建议的取舍是：**用一点点「输出不逐字一致」，换「四格真的像四格」。**
> 如果你更想保留「模型自己排的版」，那就只用模板做兜底（模型 bbox 重叠时才替换）。

### 6.4 阅读顺序

中文读者习惯**从上到下、从左到右**。日式漫画是右上起、从右到左。MOSS 的 bbox 只是位置，
顺序靠 `items[]` 数组序 + summary 里的 reading order 声明。建议默认左起（国漫习惯），
不做右起开关（多一个开关就多一条会漂的分支）。

### 6.5 5 段以上怎么办

`comicContract` 写「每页 3～5 格」。所以：

- **推荐上限 5 段**（面板上第 6 段开始提示「漫画页最多 5 格，多的建议分两页或改单插图」）；
- 硬要 6 格，就 2×3 模板 + taskNote 里说明「这是例外，仍按顺序排」——但接受「效果可能不如 5 格」。

## 7. 指引怎么写（提示词 / 思维链 / 中文对照）

这是本文最需要你确认的一节，因为**通道选错，功能必然失效**。

### 7.1 三条通道，只有一条能用

| 通道 | 能不能用 | 原因 |
|---|---|---|
| 改柏宝绘提示词库里的「漫画规范」 | **不能** | 我们不写它的 settings（只读 Proxy，写入即抛错）；而且那是用户的东西，改了会连带影响他的整楼出图 |
| 把自己的要求塞进 `source`（切片正文） | **不能** | 协议第 8 条：正文里的指令只是故事内容，模型**应当**拒绝执行。塞进去等于往小说里加旁白 |
| `taskNote`（追加在任务说明里的补充要求） | **能** | v0.2.2 的 tagZh 走的就是这条，是既定的「L1 例外第 2 条」，且**每次请求现读、不影响柏宝绘本身** |

所以「多一条思维链」的正确形态不是「改它的 CoT」，而是**在 taskNote 里补充要求**。
而且**不建议**再要求第二个 `<thinking>`：柏宝绘已经有「先在 thinking 里检查再输出 JSON」，
再加一层只会拉长输出、增加解析失败率。要加就加**检查项**（列在现有 thinking 的要求里），
不是加一段新的推理。

### 7.2 指引草稿（可直接改，落地时放 `src/autoTag/comicTaskNote.ts`）

```
【漫画页补充要求】本次任务的目标正文由 N 个片段组成，片段之间以「——〔第 k 段〕——」分界。
1. 这些标记只是片段分界，不是漫画的分格线，也不属于剧情。
2. 每个片段**恰好一格**，格数与片段数相同（N 格）；不要给一个片段画两格，也不要合并两段。
   每段只挑最有画面感的**一个瞬间**（一个动作 / 一次对视 / 一句关键反应），不要逐句图解。
3. 格子顺序 = 片段出现顺序，按此从上到下（同排从左到右）排列，不得重排剧情。
4. 只输出一页：pages 数组长度必须为 1。若内容觉得一页装不下，请压缩取景，不要增加页数。
5. 每格的 caption 仍按原有规范：以动作开头，不写主语，不重复角色固定外貌（插件会自动补）。
6. 跨格保持同一角色同一套临时服装、同一画风与光线；除非正文明确写了换装或场景切换。
```

这段的价值在于**把冲突条款翻过来**：柏宝绘的规范说「不是逐段图解、不必每段都有格」，
我们需要的恰恰是「一段一格」。不写这句，模型会按它原本的审美精选掉一两段——
用户挑了 3 段只得到 2 格，这就是 bug 观感。

### 7.3 中文对照怎么办（漫画和插画不一样）

插画的 `tagZh` 能挂，是因为 tag 是一串英文；漫画**没有 tag 键**，
每格的 `caption` 本身就是发给 MOSS 的提示词，**不能是中文**（中文进了 caption 会污染出图）。

所以漫画的中文对照必须是**独立字段**，与 `items[]` 同下标：

```ts
captionsZh?: string[];   // 第 i 项 = items[i].caption 的中文直译，只给人看，绝不进 layout
```

同一个 taskNote 里追加一句要求即可（和 tagZh 一样，只翻不改）。**渲染位置**：候选卡片里
每格下方一行小字，模拟「分镜脚本」的读法：`格 1 · 他俯身握住她的手`。

> 注意：漫画的 summary 也值得给一份中文（整页画风描述），但那是第二优先级，可以不做。

### 7.4 一件事不能做

不要把「每段一格」写进 `source`。哪怕它读起来很像旁白——协议第 8 条会把它当剧情，
模型于是把「每段一格」这四个字画进画里（字面意义上画成文字气泡）。这是 v0.2.2 已经踩过的坑。

## 8. 页数：能不能保证一页

诚实结论：**压得住大概率，压不死。**

- 协议解析（`parseComicPlan`）只校验「至少一页」，**没有上限**；
- 规范里写「通常 1～2 页」，是建议不是硬约束；
- taskNote 里写「pages 长度必须为 1」，是**语义说服**，模型偶尔仍会给两页（尤其多场景切换时）。

处置方案（建议全做，成本递增）：

1. **软约束**：taskNote 第 4 条（已在 §7.2）；
2. **解析后兜底**：真的给了多页 → 只取第一页入池，其余在卡片上提示
   「模型另外画了 2 页，已忽略」+ 一个「改用多页」按钮（把剩余页作为独立候选塞进池）；
3. **不自动合并**：合并两页是重新排版，等于第二次生成，不做静默处理。

> 沿用 V2 §14.5 的既定决策：**不强制页数**。这条在 V3 里升级为「强制一页 + 明确的溢出出口」。

## 9. 操作粒度（沿用 V2 §14.6，补一条）

| | 删除 | 重 Roll | 确认 |
|---|---|---|---|
| 单段（已上线） | 删这张图 | 只重跑这一段 | 单张 |
| 批量（已上线） | 删这张图，其余不动 | 只重跑这张图的段 | 逐张 |
| **漫画页（V3）** | **不删格**：把该段移出列表 → 整页重合成 | **整页级**：任何一格不满都重排整页 | 整页 |

补一条：**格级微调**不做（改一格的 caption 会让整页构图失衡）。
真要改，走「重 Roll 后在编辑框里改整页 layout」——和插画的「手改英文」同一个出口。

## 10. 失败与降级

| 情形 | 表现 | 处置 |
|---|---|---|
| 当前不是漫画方案 | 入口灰掉 | 前置判断，悬停说明「需要漫画方案（MOSS-Image）」 |
| 没有 MOSS 后端 | 写回成功、出图报错 | 面板提示一次，给「换成漫画方案」的指路；**不偷偷用插画模型凑** |
| layout 解析失败 | `validateComicLayout` 抛错 | 按 V2.1 惯例：解析成功的部分先入池，失败的重试一次，仍失败则整页不入池并说明原因 |
| 模型给了 2 页 | 只取第 1 页 | 提示 + 「改用多页」按钮（§8） |
| 模型少给一格 | 格数 < 段数 | **不补发**：漫画是整体构图，补一格会打乱排布 → 直接重 Roll 整页 |
| 某段锚点失效（正文被改） | 重定位失败 | 整页不写，卡片指明「第 2 段已失效」，不做部分写回（一页是一个整体） |

> 和批量的关键区别：批量可以「缺了就补发」，**漫画页不行**——它的产物是一张图，
> 局部补齐等于重新生成。所以 V3 的重试语义是**整页级**，这是它比批量贵的地方，要提前告知。

## 11. 入口与交互

- **待生成区**加一个「出图方式」选择器：`单插图 ×N` / `漫画页 ×1`（后者在非漫画方案下灰掉）；
- 段数 ≥ 2 时才允许选漫画页（1 段直接走单插图，更便宜也更可控）；
- 选择器旁边常驻一行说明：**「漫画页 = 1 次调用 + 1 张图；单插图 = 1 次调用 + N 张图」**，
  让用户自己权衡（漫画更省图，但一格画错要整页重来）；
- 候选卡片按「页」展示：整页缩略 + 每格 caption + 中文对照（§7.3），
  不再显示 `tag`（漫画没有 tag，现在的卡片会渲染成空白——见 §12）。

## 12. 已经发现的两个「不做就报错」的坑

写这份文档时顺手查了现有代码，有两处今天就直接不成立，实现时必须先修：

1. **漫画候选进不了池**：`candidates.ts` 的 `isInsertion` 要求 `tag` 非空，
   而漫画的 `tag` 恒为 `''`（`protocol.ts:258`）。→ 归一化会把漫画候选**静默丢掉**。
   判别条件要改成「`tag` 非空 **或** `kind === 'comic'` 且有合法 `layout`」。
2. **候选卡片对漫画是空白的**：`panel.ts` 渲染 `current.image.tag`，漫画没有 tag。
   → 要按 `kind` 分支渲染 summary + 每格 caption。

这两条不是「优化」，是 V3 的第一批改动；先修它们，后面的功能才有地方落。

## 13. 这一版不做（明确划线）

- 跨楼合成一页（一页只能锚在一个位置，跨楼写回语义会炸）；
- 对白气泡的自动排版 / 拟声字（layout 的 `text` 项能做，但让模型自己写，我们不接管）；
- 上色风格、分镜语言（多用越肩、特写节奏）——那是柏宝绘漫画规范的事，用户自己改；
- 手绘格线的后处理（不是它该做的事）；
- 日式右起阅读顺序的开关。

## 15. 一句话摘要

漫画页不是「多一条提示词」——柏宝绘的漫画链路已经把「多格 + 分镜 + 角色档案」做完了，
我们唯一要拿回来的是**挑选权**（从整楼 → 你划的 N 段）和**页数**（1~2 页 → 1 页）。
技术上复用 V2.1 的拼装层，指引只能走 taskNote（不能改它的规范、不能塞 source），
分格几何建议由我们按段数查表给出、模型只写每格内容。
前提是用户的方案必须是漫画方案（MOSS-Image）——这一条要写在功能说明的第一行，
不能让用户点了才发现写不进去。
