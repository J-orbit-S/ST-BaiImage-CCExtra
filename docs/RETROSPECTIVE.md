## 1. 需求从哪来

起点是一个很具体的痒：柏宝绘出图时，送进 LLM 的是**一整层楼**的正文。可我想画的往往只是其中一句——
「她把伞往我这边倾了倾，雨点打在她半边肩膀上」——但同楼前面还有三百字的对话和心理描写，模型容易被带偏，
tag 里混进不属于这一镜的元素。

于是有了最初的一句话需求：

> **正文里划一段 → 只把划中的这段送去分析 → tag 仍然按柏宝绘的规矩插回原文 → 图还是柏宝绘出。**

这句话拆开来，是七条硬约束。后面所有的架构选择，都是被这七条逼出来的：

| # | 约束 | 原文依据 | 它排除了什么 |
|---|---|---|---|
| 1 | 柏宝绘**一个字都不能改** | 「别人老师的作品，我们只是拿取并复用」 | 排除了「给上游加一个 source 覆盖参数」这条最省事的路 |
| 2 | **不留配置口子** | 「一切配置在柏宝绘里改，CCExtra 自动跟随」 | 排除了自己存一份 settings 快照的做法 |
| 3 | 但**要能自选方案** | 「柏宝绘选 A，CCExtra 用 B 出图」 | 排除了「完全跟随当前方案」的偷懒解法 |
| 4 | 分析过程**一模一样** | 「连 LLM analyses 的过程也要一样」 | 排除了「照着思路重写一遍」的理解式复刻 |
| 5 | 工作量不是问题 | 「工作量大没关系」 | 排除了所有「差不多就行」的折中 |
| 6 | 要能**长期排错** | 「这以后会成为我们的工程文件」 | 排除了「能跑就行、不留探针」的写法 |
| 7 | 一步一个里程碑 | 「我是看不懂的，你自己自查」 | 排除了大爆炸式提交 |

第 3 条和第 4 条是打架的：想自选方案，最自然的做法是自己接管出图；可一旦自己接管出图，
画师串、负面词、并发、落盘、`promptHash` 全都要重新实现一遍——**这恰好违反第 4 条**。
这个矛盾在 §3 的 Q3 和 §5 的「B 段决策」里被解掉了，它是整个项目最关键的一次取舍。

## 2. 五问：把「能不能做」问成「必须怎么做」

动手前一共问了五个问题，每个都单独出了分析文档。这五份文档的价值不在结论，在于**当时的否决理由**——
半年后如果想「为什么不走那条更简单的路」，答案都在这里。

### Q1：伴生插件能读到柏宝绘的方案 / 副 API / 接入点吗？

**结论：公开接口不能，但读设置可以。**

`globalThis.STBaiBaiImage` 只暴露了极窄的几个方法（生成、取消、读元信息一类），
**方案、副 API、接入点一个都没有**。一度以为这条路死了。

转折点是想清楚一件事：**「读不到」和「走不了公开接口」不是一回事。** 柏宝绘的所有配置都躺在
`extensionSettings['baibai_image']` 里，副 API 渠道还额外有一份跨插件共享的 `baibai_api_channels`
（带 `schemaVersion` / `revision` / 事件广播）。这些是进程内的全局对象，任何扩展都能读到。

于是分了三档：

| 数据 | 可读性 | 处理 |
|---|---|---|
| 副 API 渠道 | 🟢 官方共享键，最干净 | 直接读，跟它自己的多插件共享机制同口径 |
| 方案（NAI plans / ComfyUI workflows + promptSets） | 🟡 可读，但是私有结构 | 只读，接受「上游改结构就得跟」的代价 |
| 接入点（含 API Key 明文） | 🔴 可读，但敏感 | 只读，不落日志、不外传 |

> 否决的方案：**让柏宝绘作者给公开接口加一个 `getConfig()`**。技术上最干净，但它要求改上游一行，
> 违反约束 1。这条线到此为止，后面再没回头。

### Q2：只把「一层楼」换成「划线」，可行吗？

**结论：逻辑上可行，工程上必须复刻。**

精确地说，要换的位置是 `runner.ts` 里 `source = message.mes` 那一行——之后的清洗、拼装、
请求、解析、写回全部与它无关。理论上只要注入一个 `source` 就完事。

但 `runForFloor` 是模块私有函数，没导出、没挂全局、没有任何事件能截获它。
纯伴生插件**碰不到它**。所以「只换输入」这句话在语义上成立，在实现上等于「把整条链路复制一份，
只把输入换掉」。

那次讨论还顺带钉住了三个卡点，后面每一个都花了功夫：

1. **分析入口私有**（致命）→ 只能复刻；
2. **写回 rebase 绑定整楼正文**（可控但要处理）→ tag 的插入行号是「切片内行号」，
   而 `injectImageTags` 要的是「整楼行号」，中间必须换算（这就是 `selection/segmentPlan.ts` 存在的原因）；
3. **划线本身不是现成数据** → 得自己做 DOM 选区 → 原文区间 → 指纹。

> 否决的方案：**临时楼层 / 假消息技巧**（造一条隐藏消息，让它自动跑）。
> 否决理由：会污染聊天记录、要跟 `chat.length` 与 swipe 索引斗智、出错后无法回滚。

### Q3：能复用柏宝绘的配置，又自己指定方案出图吗？

**结论：配置能复用，但「自选方案出图」不能靠公开接口。**

决定性发现：**方案是「数据」，不是「代码」。** `settings.nai.plans` 里每个方案是全量存储的
（模型、采样器、步数、CFG、画幅、画师串、负面词、结构标签……），ComfyUI 预设同理。
柏宝绘自己的出图函数就是「拿当前方案这份数据去拼请求」——那么换个索引读，就是另一个方案。

但公开 `generate()` 的参数里**没有方案**，它内置永远用「当前方案」。所以自选方案只有两条路：

- **路 A**：自己复刻 B 段出图链路，按任意方案索引拼请求；
- **路 B**：不改出图，只把 tag 写对，让柏宝绘自己的卡片去出图。

当时倾向路 A。后来发现路 A 有个更严重的副作用，见 §5。

### Q4：能不能命令柏宝绘「临时切到 B，出完再切回 A」？

**结论：不可行。这是本次唯一被彻底判死的一条路。**

四条证据链：

1. 没有任何「切方案」的对外命令接口；
2. 切方案在柏宝绘内部只是**改一个内存变量**，连 `extensionSettings` 都不一定立刻同步；
3. 设置流是**单向**的：UI → 内存 → 回写 `extensionSettings`。外部往 `extensionSettings` 里写，
   下一次柏宝绘自己的回写就把它抹掉（更糟的是可能抹掉用户刚改的东西）；
4. 公开 `generate()` 内置「当前方案」，无法指定。

唯一的野路子是用 DOM 点击假装用户切方案：找 `.bbi-window` 判面板在不在、点方案按钮、
读 `aria-checked` 判成功、用引用计数在出图完成后切回、还要防用户此刻正在手动操作。
**技术上能写，但它把「柏宝绘改版」变成「本插件失效」**，而且与约束 1 的精神相悖（不碰它，连 UI 都不该代点）。

> 当时的原话是「可以做到，但不该做」。这条路线记录在此，是为了以后不再重新论证一遍。

### Q5：「连 LLM 分析过程都一模一样」做得到吗？

**结论：做得到，但只有一条路——逐字搬运 + 字节级校验。**

这里必须区分两个层次，混在一起就会做错：

| 层次 | 内容 | 能不能「语义等价」 |
|---|---|---|
| L1 出图 | 拿 tag 去 NAI / ComfyUI 画图 | 天然一样，因为**根本不经过我们** |
| L2 分析 | 上下文装配、提示词拼装、请求、解析、写回 | **不能**，必须字节级 |

L2 之所以不能语义等价，是因为「一模一样」的判定标准是**发给 LLM 的 messages 数组哈希相同**。
在那个数组里，一句「请为下列正文生成插画」和「请为以下正文生成插画」的差别，
会让模型行为产生无法预测的漂移——而这种漂移肉眼看不出来，只会在某天出图变差时被归咎于「玄学」。

这份认识直接决定了架构：**不做理解式重写，做搬运工。**

## 3. 架构定稿：三层 + 一道闸

```
┌─────────────────────────────────────────────────────────────┐
│  Selection Source（自有）   selection/                       │
│  DOM 选区 → 原文区间 → 指纹 → 切片行号⇄整楼行号              │
└───────────────────────────┬─────────────────────────────────┘
                            │ source = 划线切片
┌───────────────────────────▼─────────────────────────────────┐
│  Orchestration（复刻时序）  runner/                           │
│  与上游 runForFloor 逐段对应，只有两处实质差异               │
└───────────────────────────┬─────────────────────────────────┘
                            │ 读配置
┌───────────────────────────▼─────────────────────────────────┐
│  Adapter（只读）            state/settings.ts                 │
│  递归只读 Proxy，每次访问现读，绝不缓存、绝不写              │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Vendored Core（逐字复制，禁止改）  40 文件 / SHA256 校验     │
│  autoTag/  st/  backends/  api/  state/(角色库·历史)         │
└─────────────────────────────────────────────────────────────┘
```

四个决定，每个都能单独讲：

**① 为什么是「逐字复制」而不是「重写」。**
因为判定器是哈希。重写再像，注释、空格、模板字符串里的一个换行都会让哈希不同——
而一旦允许「小差异」，就没有理由拒绝第二个小差异，最后变成「差不多一样」。
逐字复制把「像不像」变成「等不等于」，这是可判定的。

**② 为什么目录要和上游同构。**
vendored 文件里写的是 `import { ... } from '@/autoTag/clean'`。若把文件挪到
`src/vendor/clean.ts`，就得改 import——**改 import 就意味着文件内容变了，SHA 立刻不匹配**。
所以保留 `src/autoTag|st|backends|state|api` 的目录形状，把 `@` 别名指向 `src`，
复制过来的文件**一个字符都不用动**。代价是自有代码（`selection/`、`runner/`、`ui/`）和上游代码混在同一层，
靠命名和 `VENDORED.md` 的登记表区分。这个代价可以接受。

**③ 为什么不直接搬上游的 `settings.ts`。**
上游那份是 `reactive<ImageSettings>` 内存单例，**任何 UI 改动都整份回写** `extensionSettings`。
照搬它，等于 CCExtra 也握着一支能写柏宝绘配置的笔——写错一次就覆盖掉用户的方案和明文 key。
所以这层是唯一「刻意不逐字」的源码：手写一个**递归只读 Proxy**，深层赋值（`settings.comfyui.promptSets = ...`）
也会当场抛错，且**每次属性访问现读**（不缓存），所以在柏宝绘里改完方案，下一次划线立刻生效。

**④ 为什么 `settingsDefaults.ts` 必须由脚本生成。**
10 份内置提示词，549 行 / 92KB 模板字符串。手抄任何一个标点走样，L2 一致性当场失效，
而且**肉眼绝对查不出来**。所以写 `scripts/extract-defaults.mjs` 从上游按常量名逐个扫描抽取，
文件头注明「脚本生成，禁手改」。

## 4. 柏宝绘这一侧到底怎么出图（被问最多的部分）

柏宝绘的「出一张图」其实是**两段**，中间用正文里的 `<bbi_image>` tag 连接。
理解这一点，才能理解本插件为什么只做一半。

```
【A 段 · 分析】一整层楼正文 ──▶ LLM ──▶ JSON ──▶ tag 写回正文
                                                    │
                                          <bbi_image>…</bbi_image>
                                                    │
【B 段 · 出图】tag ──▶ 拼画师串/负面词/方案 ──▶ NAI 或 ComfyUI ──▶ 落盘 ──▶ 卡片显示
```

### 4.1 A 段（本插件完整复刻的部分）

| 步 | 动作 | 对应模块 |
|---|---|---|
| 1 | 闸门：开关、当前聊天是否被排除、这楼是不是 AI 剧情楼、是否已处理 | `runner/runSelection.ts` |
| 2 | 取上下文：柏宝书角色状态、角色库、角色锚点、世界书、角色卡、人设 | `autoTag/bookMemory` `state/charTags` `autoTag/charAnchors` `autoTag/context` |
| 3 | 协议快照：本次用哪套 JSON 协议、哪些字段 | `autoTag/protocol` |
| 4 | 拼 prompt：6 类文本（任务、规范、思维链、画师串、正面/负面示例、剔除标签）+ **硬编码任务协议** | `autoTag/prompt.ts` |
| 5 | 清洗正文：按物理行切段、编号、给每段一个位置 ID | `autoTag/clean.ts` |
| 6 | 发请求：副 API 或跟随主 API（**渠道二选一**），超时/取消/历史 | `api/client.ts` `state/history` |
| 7 | 解析：JSON → changes，**校验失败就在循环内重试** | `autoTag/protocol.ts` |
| 8 | 后处理：changes → ops、`@` 角色占位符替换、漫画方案补外貌 | `runner/plan.ts` |
| 9 | 写回：CAS（指纹不符就 rebase 重定位，再不符就放弃） | `st/messageEdit.ts` |
| 10 | 反馈：成功/失败提示、`extra.bbiCharChanges` 落账 | `runner/runSelection.ts` |

第 4 步里的**硬编码任务协议**是最容易漏的地方：用户能在柏宝绘里改的是那 6 类文本，
但「你是一个插画提示词工程师……输出 JSON……字段名 X」这段是写在源码里的。
漏掉它，messages 就少一整段——所以它也在 vendored 清单里，且由黄金哨兵按哈希钉死。

### 4.2 B 段（本插件刻意不做的部分）

一次关键发现让 B 段的方案彻底改写：

> 公开 `generate()` **返回 dataUrl，可选落盘图库，但不写楼层 `extra`**。

`PublicGenerateResult` 里根本没有 slot 概念——图不会挂到任何卡片上。
如果 CCExtra 自己调它，用户看到的是：**图库里有图，但楼层卡片还是「待生成」**。
这比不做更糟：用户会以为失败，再点一次，于是图库里堆两张一样的。

所以 B 段的最终形态是：**CCExtra 只负责把 tag 写对，出图交回柏宝绘的卡片，用户点一下。**

看起来像是「少做了一步」，实际是**用一次点击换零漂移**：

| 交给柏宝绘的东西 | 自己实现的风险 |
|---|---|
| 画师串拼接、vibe、负面词 | 少一个逗号，风格就跑 |
| 并发闸门、队列 | 连点三次可能三张图同时打 API |
| 落盘三层 + 破指针降级 | 图存错目录，卡片永远显示不出来 |
| `promptHash` / stale 判定 | 卡片该不该「待生成」判断错，用户反复重出 |
| 方案里的模型/采样器/画幅锁 | 与用户在柏宝绘里看到的设置不一致 |

至于「能不能自动点一下卡片」，答案是能，但只能靠 DOM 点击——柏宝绘的 `autoGenerate` 标记是
**它进程内的内存 Map，第三方无法置位**。要自动化就得靠按钮选择器，而选择器会随它改版失效。
这条线留了个口子（默认不做），理由写在 §9。

## 5. 落地：八个里程碑，一次一个

| 阶段 | 交付 | 验收证据 | 实际耗时占比 |
|---|---|---|---|
| **M0 锚定** | 上游 pin `d6c5519` / v0.3.6，`VENDORED.md` 登记表 | `verify:upstream` 能跑 | 5% |
| **M1 纯函数搬运** | clean / protocol / rebase / slotPlan / excludes / imageTagRegex / size / mossLayout / nai 判定 | 上游单测原样跑通（115 条） | 10% |
| **M2 Adapter** | 只读设置 Proxy、共享渠道、角色库重放、上下文/锚点/柏宝书 | `settings.adapter.test.ts` | 15% |
| **M3 提示词层** | `prompt.ts` 逐字 + 10 份内置常量脚本抽取 | 黄金 messages SHA256 首次对拍 | 15% |
| **M4 解析层** | protocol 解析 + changes 后处理 + `@` 替换 | 黄金 plan + `runner/plan.test.ts` | 10% |
| **M5 选择源** | `selection/` 定位、捕获、指纹、切片⇄整楼换算 | 52 条划线用例 | 20% |
| **M6 编排写回** | `st/messageEdit.ts` 逐字 + `runner/runSelection.ts` | 端到端：假宿主 + 真上游代码 | 20% |
| **M7 一致性常驻** | 三道闸 + 诊断前缀 + 文档 | 三闸全绿 | 5% |
| **M8 面板与入口**（v0.2.0） | 偏好层 + 面板 + 魔术棒 + 🍃 悬浮球 + 取消在途分析 | 33 文件 / 509 tests；`npm run smoke` 三处入口全挂 | 10% |

**为什么要按这个顺序。** M1–M4 是「把上游搬进来并证明没搬坏」，它们的验收物是**上游自己的测试**——
不需要我相信自己，只需要上游的测试全绿。M5–M6 才是新写的代码，验收物是**新写的测试**。
把「搬运」和「创作」严格分开，好处是出问题时能一秒定位在哪一侧：
**上游测试挂 = 搬运出错；只有划线/编排测试挂 = 新代码出错。**

### 5.1 实打实的两处差异

整套东西只有两处和柏宝绘不同，这是设计的自我约束——**出现第三处就该被 review 拦下**：

| # | 差异 | 位置 | 为什么必须有 |
|---|---|---|---|
| ① | 送给 LLM 的 `source` = 划线切片（不是整楼 `mes`） | `runSelection.ts`，对应上游 281–296 行 | 这就是整个插件的存在理由 |
| ② | 写回时 rebase 的基底用**整楼现文**（不是切片） | `runSelection.ts`，对应上游 547–585 行 | tag 要插回整楼的正确位置 |

其余全部照抄，包括那些看起来可以简化的地方：重试循环、validate 内解析、
`extra.bbiCharChanges` 的字段形状、失败文案的语义、记忆与角色库**仍按整楼取**（不因划线缩小）。

> 「记忆与角色库仍按整楼取」这条当时反直觉：既然只画一段，为什么上下文不一起缩小？
> 因为角色库和柏宝书讲的是「这个世界此刻的状态」，与「这一段写了什么」无关。
> 缩小它，模型就不知道这个角色穿的是校服还是铠甲——tag 会飘。这也正是「分析过程一模一样」的一部分。

### 6.1 最关键的一次发现：rebase 会锚错行

这是整个项目技术含量最高的一处，单独说。

上游用 `rebase` 在正文变动后重新定位 tag 的插入点，它的对齐锚是**整行文本相等**。
于是出现一个致命场景：

```
第 3 行  「你回来了。」
第 9 行  「你回来了。」
```

用户划了第 9 行，tag 应该插在第 9 行之后。但 rebase 找「你回来了。」时，会先撞上第 3 行，
于是图插到了三百字之前。**用户几乎不可能察觉**——他只看到图出来了，只是位置不对。

结论：**切片内行号不能直接当整楼行号用**，必须自己换算。于是有了 `selection/segmentPlan.ts`：

```
capture.range.start ──lineIndexAt──▶ 切片起始绝对行
                                      ＋ segment.sourceLine = 绝对行
```

`sliceSegments`（给模型看的）与 `absoluteSegments`（写回时对齐的）**同下标一一对应**，
中间只差一个行号偏移，且共用同一份清洗结果——避免「给模型看的」和「写回对齐的」口径漂移。
`segmentPlan.test.ts` 里有一条对照用例专门钉住这个坑，防止以后有人「顺手简化」掉。

### v0.2.0 — 2026-11-20（面板 / 三处入口 / 取消）

**需求**：想选「自动出图 or 自己点卡片」；面板 UI 跟柏宝绘一致；加魔术棒入口与 🍃 悬浮球；

**先查清三件事**（详见 ENGINEERING §13.9）：柏宝绘**自己就有**悬浮球和顶栏按钮；它的样式挂在

| 改动 | 文件 |

## 11. 改动守则（每次动代码前看这一节）

### 11.1 两个路径，一个真源

| 路径 | 角色 | 能不能手改 |
|---|---|---|
| `G:\插件\ST-BaiImage-CCExtra` | **开发真源**，git 仓库 | ✅ 只在这里改 |
| `G:\SillyTavern\public\scripts\extensions\third-party\ST-BaiImage-CCExtra` | **安装副本**，SillyTavern 实际加载的 | ❌ 改了会被下次同步覆盖 |

同步命令：`npm run sync:st`（等价于把 `manifest.json` + `dist/index.js` 拷过去）。
**改完必须 build 再同步**——直接拷 `src/` 过去没用，ST 加载的是 `dist/index.js`。

### 11.2 一次改动的完整流程

```bash
# 1 改源码
# 2 三道闸，缺一不可
npm run typecheck
npm test
BAIBAI_UPSTREAM=<柏宝绘路径> npm run verify:upstream

# 3 构建 + 冒烟 + 同步安装副本
npm run build
npm run smoke      # 动了 ui/ 或入口时必须跑：产物加载得起来、三处入口挂得上
npm run sync:st

# 4 入库并推送
git add -A && git commit -m "..." && git push
```

> `smoke` 是 v0.2.0 加的第四道闸。它不检查逻辑，只检查「构建出来的东西是不是残废的」：
> 产物能不能加载、调试出口在不在、菜单/球/面板有没有真的挂上去。
> 纯 UI 改动用它兜底——面板这类代码的单测只能覆盖结构，挂载时机只有真宿主才知道。

**红绿灯怎么读**：

- `verify:upstream` 红 → vendored 代码被改过（或换行被转换）。**先恢复，不要「顺手接受」**；
- 黄金哨兵红 → 发给 LLM 的 messages 变了。确认是新需求还是 bug，是需求就用
  `GOLDEN_UPDATE=1` 更新基准并在 commit message 里写清原因；
- 只有划线/编排测试红 → 新代码的问题，与上游无关。

### 11.3 柏宝绘升级了怎么办

1. `git -C <柏宝绘> pull` 拿到新版，记下新 commit；
2. 先跑 `verify:upstream`：
   - **全绿** → 上游没动我们搬的部分，改 `VENDORED.md` 的 pin 即可；
   - **有红** → 上游协议变了。先看 diff 判断是「重命名/重构」还是「真改逻辑」，
     逐条对拍后再更新 vendored 文件，然后跑黄金哨兵确认 messages 的变化是否符合预期；
3. 黄金哨兵更新后，`docs/ENGINEERING.md` §6 的提示词清单要同步。

### 11.4 三条红线

1. **不要为了「更好」而改 vendored 文件。** 要改就回上游改，再重新复制。
2. **不要增加第三处与柏宝绘的实质差异。** 现有两处（划线作 source、rebase 用整楼）是设计底线。
3. **不要在没有 `extra` 写入的情况下自己出图。** 结果是「图库有图、卡片空着」，比不做更糟。

## 12. 一句话总结

这个项目没有发明任何东西。它做的事是：**把别人已经做对的一条链路，逐字搬到自己的进程里，
然后只改其中一行输入，再用三道机器闸门保证「除了那一行，别的都没变」。**

难的不是写代码，是忍住不改。每一次「这里可以写得更漂亮」，都在把「一模一样」变成「差不多」。
