## 1. 需求原文（不改写，供以后核对）

工作流程（用户原文）：

1. 鼠标划选 AI 正文中喜欢的句子或段落。
2. 自动识别它属于哪个楼层、哪一段。
3. 点击「生成 tag」。
4. 读取当前楼层前后的剧情上下文、角色卡、世界书，以及柏宝绘在该楼层的角色档案。
5. 通过独立配置的副 API 生成指定画面的 tag。
6. 显示候选结果，用户确认后插入楼层。
7. 可以随时重新 Roll、编辑、删除。

核心设计意图（用户原话）：

> 选中的句子只是画面定位锚点，不是 AI 唯一能看到的文本。  
> 例如你划选的是「你今天怎么这么乖？」，AI 应该同时读到前面的拨头发动作、后面的指尖停留，以及两个人当时的关系，而不是只把一句话翻译成一张人物说话的图。这样才有可能挑出真正值得画的瞬间。

三段分离（用户原话，明确要求**不要绑在一起**）：

| 操作         | 实际行为               | 花谁的额度    |
| ---------- | ------------------ | -------- |
| 生成 tag     | 副 API 读上下文，生成画面提示词 | 副 API 文本 |
| 重 Roll tag | 保留选段和上下文，重新生成一版提示词 | 副 API 文本 |
| 生成图片       | 用户确认 tag 后，交给柏宝绘出图 | 柏宝绘图片    |

> 以及：每个指定段落有自己的 ID，重 Roll 只更新当前段落的 tag，不影响同一楼的其他画面。

**修订（2026-11-20 当天，讨论后）**：上面「核心设计意图」里那段「AI 应该同时读到前面的拨头发、后面的指尖停留」**没有采纳**——  
结论是不加同楼旁文，喂给模型的只有切片。理由与代价见 §3，原文保留在此仅作溯源，不再作为实现依据。

## 3. 同楼旁文：**已否决**（2026-11-20）

### 3.1 问题确实存在（留档，免得以后重开讨论）

`runSelection` 喂给 LLM 的目标正文**只有切片**，上下文楼又是这么取的：

```ts
// src/autoTag/prompt.ts:182-191
const previous = recentFloors(context, targetFloor, options.contextMessages)
  .filter(floor => floor !== targetFloor)   // ← 本楼被整个排除
```

所以划「你今天怎么这么乖？」时，同一楼里前面那句「把她散落在脸颊边的头发拨到耳后」、后面那句「指尖却没有立刻离开」，模型一个字都看不到。

### 3.2 决定：不做

> 用户原话：「做不到就不要硬做，反正我们也只是切片。」

这条不做是**有意的上限**，不是遗漏。收益是口径干净：

- **L1 例外清单仍然是 1 条**（只有 `source` 一处不同）。`ENGINEERING.md §1` 的表格、`verify:upstream` 的对拍口径，一个字都不用改。
- 「把切片当成一整楼」这个心智模型继续成立，排错时不需要追问「多出来的那一段是从哪来的」。

代价（已知并接受）：模型看不到锚点前后的动作，画面会更贴着那一句话本身。这是「只给切片」这个前提自带的天花板。

### 3.3 以后若要重开，落点在这里

- 改 `prompt.ts:182` 那处 `filter`，加一个**默认关**的开关；
- 同楼旁文要做成「只读参考段」，插在 target 之前；已插的 `<bbi_image>` 必须涂白（复用 `maskImageTags`，保行号）；
- **动手前必须先改 `ENGINEERING.md §1`**：L1 例外从 1 条变 2 条。不改文档直接改代码，`verify:upstream` 会对不上，且以后没人说得清「为什么 messages 变了」。

## 4. 架构：把一条链切成三段

现状是一条链（`runSelection` 一口气跑到底）：

```
划线 → 装配上下文 → 副 API → 解析 → changes/ops → 写回正文 → 点卡片出图
```

Volume 2 在「解析之后、写回之前」切一刀：

```
【A 生成 tag】  划线 → 装配上下文 → 副 API → 解析 → ImagePlan ─┐
                                                              ↓
【B 人工确认】  候选池（段落 ID）→ 确认 / 重 Roll / 编辑 / 删除  ← 本地，零 API
                                                              ↓
【C 写回 + 出图】 重定位锚点 → 写回正文（rebase 现文）→ 自动/手动点卡片
```

### 4.1 代码上的切点（几乎不用改逻辑）

| 段 | 来源                                                   | 处置                                                                            |
| - | ---------------------------------------------------- | ----------------------------------------------------------------------------- |
| A | `runSelection.ts` 130–300 行（闸门 / 上下文 / 请求 / 重试 / 解析） | 抽成 `analyzeSelection(capture, opts) → Candidate`，末尾**不写回**                    |
| B | 全新 `state/candidates.ts` + `ui/panel.ts` 列表          | 新写                                                                            |
| C | `runSelection.ts` 302–400 行（ops / 写回 / 槽位迁移 / 出图）    | 抽成 `commitCandidate(candidate, opts)`，**逻辑一行不改**，只把数据源从「刚拿到的 plan」换成「候选池里那一版」 |

C 段之所以能整段复用：它本来就不认识「plan 从哪来」，只认结构。

### 4.2 三种模式，同一条 A 段

```
① 全自动（默认）  自动出图=开，需确认=锁死关  →  A → 直接 C（含出图）   = v0.2.0 原样
② 确认式          自动出图=关，需确认=开      →  A → 候选池 → 人工 → C（含出图）
③ 全手动          自动出图=关，需确认=关      →  A → 直接 C（只写 tag）
```

三条走的是同一个 A 段，差别只在「A 之后调不调 C，以及调之前过不过人工」。互锁规则见 §7。

### 4.3 多段落批量：A 段**前面**多一个拼装层

V2.1 在 A 段之前加一步：把待生成列表里的 N 段拼成一个**伪楼层**，A 段本身完全不变（它只认识一份 target）。

```
N 段 → 拼装伪楼层 → A → 候选池（N 张，各自引用一段）→ 人工 → C
```

拼装与归属的细节见 §14.2 / §14.3。这一步是批量和漫画页**共用**的，所以先做批量不会把漫画页堵死。

## 5. 数据模型

### 5.1 段落 ID

```
segmentId = hash( chatId | floor | swipeId | anchorText | 同楼第 n 次出现 )
```

三个刻意的选择：

1. **不含内容 hash / 不含版本号** → 重 Roll 不换 ID，所以「同一段的多版候选」天然挂在同一个 ID 下，历史版本也能留。
2. **含「同楼第 n 次出现」** → 同一句话在一楼里出现两次也能区分（`locate.ts` 已经能做消歧，这里只是把结果固化）。
3. **含 chatId / floor / swipeId** → 换聊天、换 swipe 绝不串味。

### 5.2 候选单元：**图是单位，段只是引用**

> 这一节在 2026-11-20 讨论多段落批量时改过一次。  
> 原写法是「一个 segmentId 下面挂多版图」，那个模型**会把漫画页彻底挡死**（漫画是「三段 → 一页」，段画不出这种关系）。现在是图优先。

```ts
interface SegmentRef {
  segmentId: string;
  /** 锚点快照。不只是行号——确认有时间差，行号一定会漂。 */
  text: string;            // 选段原文（= 该段的目标正文）
  before: string;          // 选区前 ~200 字（重定位消歧用，喂给 locateSelection）
  after: string;           // 选区后 ~200 字
  startLine: number; endLine: number;   // 生成时的行号，只作参考/诊断
}

interface ImageCandidate {
  imageId: string;
  chatId: string; floor: number; swipeId: number;
  /** 这张图取材于哪几段。单插图 = 长度 1；漫画页 = 长度 N（§14.5，暂不落地）。 */
  segmentIds: string[];
  /** 整套 plan 快照，不是一串 tag 字符串。 */
  versions: Array<{ images: ImagePlanImage[]; changes: PlanChange[]; createdAt: number }>;
  activeVersion: number;
  status: 'pending' | 'committed' | 'discarded';
}
```

两条要点：

1. **段仍然有 ID**（用户的硬要求：重 Roll 只动当前段），但它不再是候选的容器，而是**图的引用目标**。重 Roll 一张图 = 用它的 `segmentIds` 重建锚点 → 重跑。
2. **为什么必须存整套 plan 而不是 tag 字符串**：LLM 的返回里除了 images，还有 `changes`（角色外形建档 / `@替换` / 漫画 `pages`）。只缓存 tag 文本，确认时就没法把建档一起落盘，角色库里会缺人——后续所有画面都丢外貌锚点。

### 5.3 存在哪：`chatMetadata`，不是 `extensionSettings`

| 存储                                         | 结论     | 理由                          |
| ------------------------------------------ | ------ | --------------------------- |
| `extensionSettings['ST-BaiImage-CCExtra']` | ❌ 不放候选 | 那是全设备全局的；换聊天会把 A 聊的候选带到 B 聊 |
| `chatMetadata['ST-BaiImage-CCExtra']`      | ✅      | 候选属于「这一次聊天」，随聊天备份/删除，天然隔离   |
| 内存                                         | ❌ 单独用  | 刷新页面就丢，用户刚生成 4 段全没了         |

读写口径照抄 `state/imageSlots.ts`：**CAS + 结构不认识就跳过**，绝不因为候选池坏了把主流程打断。

### 5.4 锚点漂移：确认时必须重新定位，不能复用 capture

`planSelection()` 第一行就是硬闸：

```ts
if (hashText(mes) !== capture.sourceHash) return { ok: false, reason: 'stale' };
```

确认发生在几分钟（甚至几天）后，正文很可能已经变过。所以确认路径要走：

```
replanCandidate(anchor, currentMes):
  locateSelection({ raw: currentMes, domText: anchor.text, before: anchor.before, after: anchor.after })
    → 新 range → 造新 capture（sourceHash = 当前正文）
    → planSelection(新 capture, currentMes, stripTags)
    → 得到可写回的 selectionPlan
```

复用全部行号换算，同时绕开 `stale`。若重定位失败（那段话被改掉了）：**不写、给一句人话、保留候选**，绝不「插到附近」——那会做出一张跟文字对不上的图，比失败更糟。

一张图引用多段时（批量、漫画页），`segmentIds` 里**每一段都要重定位成功**才算通过；任一段失败就整张不写，并且在卡片上指明是哪一段失效了，而不是笼统报「失败」。

## 6. UI 设计（照用户的交互示意来）

### 6.1 浮出工具栏（改造 `ui/trigger.ts`）

```
┌────────────────────────────────────────┐
│ 🍃 生成 tag    ＋ 加入列表    ✕ 取消     │   ← 浮在选区右下角，fixed 定位，钳进视口
└────────────────────────────────────────┘
```

两条已有纪律**必须原样保留**，否则这个功能会当场坏掉：

1. **`mouseup` 当场把选区算成快照**（浏览器下一次点击就清选区了）；
2. **按钮 `mousedown` 必须 `preventDefault()`**（否则按第二个按钮时选区已没了）。

三个按钮的分工：

- **生成 tag** = 单段模式，立刻发请求（就是现在的行为）。
- **加入列表** = 攒着，进 §6.2 的待生成列表，稍后一次发。**不调 API**。
- **✕ 取消** 不是关掉工具栏，而是**丢弃本次选区**（误划时的出口）。真正的重 Roll / 删除在候选卡片上。

> 加第三个按钮的代价：工具栏变宽，小屏上更容易挡住正文。所以「加入列表」只在长度合适时才露出——但不要把主按钮挤掉。

### 6.2 待生成列表（攒段的地方）

```
┌─ 待生成 · 3 段 ──────────────────────┐
│ 出图方式： [ 单插图 ×3 ] [ 漫画页 ×1 ]│   ← 漫画页灰着，§14.5 暂不落地
│                                       │
│  1. 他低头吻她的手背。            ✕   │
│  2. 她伸手替他整理领带。          ✕   │
│  3. 他把人抱起来放到桌面上。      ✕   │
│                                       │
│              [ 一次生成 3 个画面 ]     │
└───────────────────────────────────────┘
```

要点：

- 列表**按划选顺序**排，这个顺序就是 §14.2 拼装的顺序，也是「第 1 格 / 第 2 格」的编号来源。
- 每条都能删（还没花钱，随便删）；删完不足 2 段时，按钮回落成「生成 tag」（单段模式），别让用户对着一个只剩 1 条的列表发呆。
- 列表也存 `chatMetadata`，但它是**临时态**：发出去（拿到候选）或切聊天就该清空。
- 「出图方式」是**生成前**的选择，因为它决定让模型按哪种格式回答；生成之后改不了，只能重来。

### 6.3 候选卡片（放我们自己的面板里）

沿用柏宝绘的样式（面板已经挂在 `#bbi-app-host` 的 shadow 上，`.bbi-*` 类现成）：

```
┌─ 第 12 楼 · 2 段待确认 ────────────────┐
│                                         │
│  画面 01                      [待确认]  │
│  2people, close-up, intimate moment,    │
│  a man gently tucking a woman's hair…   │
│  [ ✓ 确认 ]  [ ⟳ 重 Roll ]  [ ✎ 编辑 ]  │
│                                         │
│  画面 02                      [已确认]  │
│  …                                      │
└─────────────────────────────────────────┘
```

要点：

- **一张图一张卡，独立确认**——AI 一次给 2 张时，很常见「一张好一张废」，不能捆在一起确认。
- **卡片头标出处**：单段时写「第 12 楼」，批量时写「第 12 楼 · 第 2 段」。点这个标记能高亮回原文那一句——出处是协议里 `position` 现成带着的（§14.3），不用额外记。
- **`编辑`** = 卡片里的 tag 文本变成 `textarea`，改完直接改候选，**不重跑 API**（改一两个词不该花额度）。
- **`重 Roll`** = 只对这张图的 `segmentIds` 重新请求，其余卡片不动。
- **重复生成** = 对同一段再点一次「生成 tag」不新建候选，而是给同一张图追加一个 version 并切到最新（§5.1 的 ID 规则保证这一点）。
- **`删除`** = 丢弃这一条候选（`status: 'discarded'`），不留痕、不写正文。
- 面板关掉再打开，候选还在（在 `chatMetadata` 里）。

### 6.4 文案上必须说清的一句话

> 重 Roll 只会换提示词，**不会重新出图**。

否则用户会以为重 Roll 顺带把图也重画了，然后发现图没变——这正好是用户想避免的那种「额度浪费」的认知反面。

## 7. 开关设计：一个开关，和它管着的另一个开关

### 7.1 两个存储项

```ts
autoGenerate: boolean    // v0.2.0 已有，默认 true
confirmTag: boolean      // 新增，默认 false
```

### 7.2 交互规则（2026-11-20 定案）

- **自动出图 开** → 需确认 **强制关闭且置灰、点不动**。  
  理由：自动出图开着时，「划线 → 写 tag → 出图」已经是一条完整闭环，中间再插一步确认没有意义；两格语义会重复，UI 上还会自相矛盾。
- **自动出图 关** → 需确认 **可选**
  - 需确认 **开** → 生成候选，**确认之后自动出图**（确认就是出图的许可）
  - 需确认 **关** → tag **无须确认直接写入**，出图由你手动点卡片


三条合起来正好是 §4.2 的三种模式：

| 模式 | 自动出图 | 需确认 | 划线之后发生什么 |
| --- | --- | --- | --- |
| 全自动（默认） | ✅ 开 | 🔒 锁死关闭 | 写 tag → 自动出图 |
| 确认式 | ⬜ 关 | ✅ 开 | 生成候选 → 你确认 → 写 tag → 自动出图 |
| 全手动 | ⬜ 关 | ⬜ 关 | 写 tag → 自己点卡片 |

> 「确认式」里那个**不是矛盾**：关掉的是「不问你就出图」，确认之后出图是拿到了你的许可。
> 所以面板上「需确认」的说明要写成「**确认后立即出图，不再二次询问**」，别让人以为还要再点一次。

### 7.3 互锁必须做在状态层，不能只做在 UI 上

只把 checkbox 置灰是不够的：用户能手改 `settings.json`，旧版本也可能写下非法组合。所以互锁落在 `normalizePrefs()` 里（纯函数，可直接单测）：

```ts
const autoGenerate = asBoolean(raw.autoGenerate, true);
// 自动出图开着时，需确认一律视为关：非法组合静默回落，不报错
const confirmTag = autoGenerate ? false : asBoolean(raw.confirmTag, false);
```

三条纪律：

1. **顺序要对**：先算 `autoGenerate`，再用它压 `confirmTag`。反过来会漏。
2. **静默回落，不弹错**：这是「组合非法」而不是「文件坏了」，不该打断任何流程。
3. **面板上的置灰只是投影**：UI 读 `readPrefs()` 的结果去设 `disabled`，自己绝不算互锁。否则两个地方各算一遍，迟早不一致。

### 7.4 主动放弃的那一格

`自动出图=开 + 需确认=开`（确认之后**不**出图、只写 tag）不再可达。

功能上确实少一种组合，但它的实际用途（先看 tag 写得对不对，再决定出不出图）已经被「确认」这一步本身覆盖了——确认就是那个「看」。

若 V2.1 发现真有这个需求，解锁方式是：`confirmTag` 打开时，让 `autoGenerate` 从「锁死」变成「可选」，语义改成「确认后是否出图」。代码不用重写，只改 §7.3 那条压制规则。

### 7.5 「独立配置的副 API」：复用 `tagGen` 指派（定案）

渠道真身共享在 `extensionSettings['baibai_api_channels']`，用 `assignments.tagGen` 指派；未指派则跟随主 API。

用户要的「独立配置」实质是「**不要让 tag 生成挤占主对话的 API**」——共享渠道 + `tagGen` 指派已经满足，而且换 key 只改一处，不用在两套 UI 里填同一个密钥。

**不预留** `tagChannelOverride`：真需要时加一个字段就能覆盖，现在留着只会变成没人敢删的死代码。

        │

## 14. 多段落批量与漫画页

> 2026-11-20 追加。用户提问：「一楼三个特别喜欢的地方，能不能分别划选、放进待生成列表、一次性让副 API 分析三个画面？」
> 以及：「以后想做漫画页，划多段落合成一页，这两个功能会不会冲突？」

### 14.1 结论

| 功能 | 做法 | 时点 |
| --- | --- | --- |
| **多段落批量（N 段 → N 张单插图）** | **做** | V2.1 |
| **漫画页（N 段 → 1 页 N 格）** | **设计留档，先不落地** | 挂起（§14.5） |

两者共用同一个「待生成列表」和同一个拼装层，**只在最后一个岔路口分叉**（渲染目标）。所以先做批量，不会把漫画页堵死。

```
待生成列表 → 拼装伪楼层 → 一次调用 ─┬─ perSegment（批量）→ N 张图，各自独立
                                  └─ composite（漫画页）→ 1 页 N 格，整页一起
```

### 14.2 拼装层：N 段变成一个伪楼层

一次调用只吃一份 target，所以必须先拼。

1. 按列表顺序把各段原文**按行**拼起来，段间插一行分隔标记（如 `——〔第 2 段〕——`）；
2. 对拼好的整串跑一次 `prepareTargetText` → 得到**全局唯一**的 `P1…Pn`（每段自己编号会撞车，所以必须拼完再编一次）；
3. 留一张反查表：伪楼行号 →（段序号，段内行号）→ 真实行号。

这套换算 volume 1 已经做过一遍（`selectionPlan`：切片行号 ⇄ 整楼行号），这里是同一件事的 N 段版。

> 段界标记的坑：它是我们塞进去的，不是叙事。要选一种**清洗规则不会删、模型也不会当成正文**的形式，并在 taskNote 里声明「这不是正文」。

### 14.3 归属：`position` 本来就是答案

协议里模型输出的位置是**段落 ID**，不是行号：

```ts
// protocol.ts:192-204
const positions = new Map(segments.map(segment => [segment.id, segment.sourceLine]));
const position = sanitizePosition(entry.position ?? entry.id, index);
const sourceLine = positions.get(position);   // undefined 就整条报错
```

所以「这张图属于哪一段」不需要新增字段：

```
模型给 P7 → 反查表 → 伪楼行号 26 → 落在第 2 段的区间 → 属于第 2 段 → 真实行号 41
```

**副产品**：出处可以直接回指。卡片头写「第 12 楼 · 第 2 段」，点一下高亮回原文那一句——因为 `position` 一路都在。

### 14.4 一次调用出 N 张

- 张数靠 `minImages = maxImages = N`。`prompt.ts:272-274` 那句「images 数量必须在 min～max 之间」本身就是最硬的锁，不用另写约束。
- 但它**只锁总量，不锁分布**：模型完全可能给第 1 段 2 张、第 2 段 0 张。所以还要：
  1. taskNote 里写「每段恰好一张」；
  2. 解析后**逐段校验覆盖**；
  3. 缺的那几段走**单段模式补发**，追加进同一个候选池。
- 补发是常规路径，不是异常处理。理由和用户定的三段分离原则一致：**不要为了少一张图，把整批重跑一遍。**
- 一次调用真正的收益在系统提示词：NAI spec / jailbreak / 世界书 / 角色卡都很长，N 次调用等于重复塞 N 份。

### 14.5 漫画页：先不落地

内核里**已经是完整功能**：`profile.comic`、`parseComicPlan`、MOSS 分镜 layout 都在，`runSelection` 现在就会在漫画方案下按 `pages[]` 输出。我们差的只是「原料从整楼换成挑出来的段」。

先不做，有三个具体原因（不是懒）：

1. **页数由模型定**。协议明写「页数由 AI 按内容定」，要强行压成「就一页」，只能靠说明书说服，稳定性比单插图低一档。
2. **协议装不下「一页来自三段」**。`pages[i].position` 是单值，一页只能声明锚在一个位置。出处只能记在我们自己的 `segmentIds[]` 里（§5.2 已经为此改好模型）。
3. **操作粒度完全不同**（§14.6），需要一套「整页级」的确认/重 Roll 语义，值得单独一版来做。

将来做的时候，这几条是定好的：

- 出图方式选择器的第二项（现在灰着，文案写「暂未开放」）；
- **不强制页数**，接受「偶尔它自己拆成两页」，并给手动合并的出口；
- 重 Roll 是**整页级**（构图是整体，改任一段都要重排）；
- 「删掉一格」= 把那一段移出列表重新合成，不是在页上抠洞。

### 14.6 操作粒度（必须提前定，否则实现时必扯皮）

| | 删除 | 重 Roll | 确认 |
| --- | --- | --- | --- |
| 单段（V2.0） | 删这张图 | 只重跑这一段 | 单张 |
| 批量（V2.1） | 删这张图，其余不动 | 只重跑这张图的段 | 单张，逐张确认 |
| 漫画页（挂起） | **不删页**，改「移出列表重合成」 | **整页级** | 整页 |

### 14.7 失败怎么收场

风险清单在 §8 R8–R12，这里只说处置顺序：

1. 解析成功的部分**先入池**，不全丢；
2. 缺的段按段补发（单段模式），补到的追加进池；
3. 补发仍失败的，那一段在列表里标红，其余照常确认；
4. 全程只提示一次汇总（「3 段里 1 段没生成成功」），不要每段弹一个 toast。

### 14.8 跨楼批量

用户举的例子都是同一楼，但列表不拦跨楼。跨楼时要**按楼分组**，每楼调一次 `applyMessageText`：

- 各楼独立写回，任一楼失败不回滚其他楼（回滚三栋楼比局部失败更糟）；
- 结果**逐楼报**：「第 12 楼写入 2 张，第 14 楼写入失败（正文已改）」；
- 槽位迁移（`migrateImageSlots`）也逐楼做——它是按楼算的。

## 15. 一句话摘要

把 `runSelection` 在「解析完」与「写回」之间切一刀，中间放一个候选池（存 `chatMetadata`），
确认才落盘 —— 于是「生成 tag / 重 Roll / 出图」彼此独立、各花各的额度。
候选池的单位是**图**，段只是图引用的目标，所以「一段一张」和「多段一张」共用一套模型。
多段落批量再加一个拼装层（N 段拼成伪楼层），一次调用出 N 张，归属靠协议里现成的 `position`。
喂给模型的仍然只有切片，不补同楼旁文：这是我们选定的上限，不是遗漏。
漫画页设计留档但先不落地——它和批量只差最后一个岔路口，晚做不会返工。
其余全部复用 volume 1 已跑通的链路，柏宝绘一个字节不动。
